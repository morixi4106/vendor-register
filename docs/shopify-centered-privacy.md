# Shopify中心の個人情報最小化

## 目的と範囲

購入者情報の主要な保管先はShopifyとし、アプリの複製と店舗への不要な表示を減らす。
店舗登録、商品・在庫管理、KOMOJU、Shopify Payments、売上・返金台帳は維持する。
この実装は運営の責任を免除するものではなく、国外移転、委託契約、本人請求、事故対応の運用確認は別途必要。

## 実装内容

| 対象                               | 変更                                                                                                                                                                    |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 新規注文のアプリ側スナップショット | 購入者氏名・メールを保存しない。金額、商品、国、Shopify参照ID、法務証跡は維持                                                                                           |
| 店舗の注文一覧                     | 購入者名・メール・配送先を一覧へ複製しない                                                                                                                              |
| 配送先                             | ログイン済み店舗に紐づく、同一Shopifyストアの支払済み注文だけをShopifyから都度取得。全額返金・キャンセルは拒否。ブラウザに永続保存せずno-store                          |
| 店舗登録の非公開連絡先             | 氏名、メール、電話、住所、登録メモ、管理メールをAES-256-GCMで暗号化。メール検索はHMAC                                                                                   |
| 公開店舗プロフィール               | `publicAddress`・`publicDescription`だけを使用。登録時の非公開住所・メモは公開へ流用しない                                                                              |
| 店舗ログイン                       | 確認コードHMAC、10分、失敗5回、再送時に旧コード失効、同時再使用防止、IP・メール・全体の送信制限。セッションはランダム256bitトークンのSHA-256をDBへ保存、8時間           |
| Shopify API認証                    | 公式PrismaSessionStorageを拡張し、access/refresh tokenだけ暗号化。SDKには復号して渡す                                                                                   |
| 問い合わせ                         | 現行受付を維持し、DBの本文・連絡先・返信を暗号化。運営通知メールに本文を複製しない                                                                                      |
| Inbox移行                          | 受信確認とお問い合わせページの移行確認の両方を運営が記録してから旧APIを410にする。Inboxを自動インストールしない                                                         |
| 開示・削除Webhook                  | Shopify署名検証、対象ストア照合、再送重複排除、最小参照情報を永続受付。対応期限30日。受信だけで削除・完了とはしない                                                     |
| 対応管理                           | 所有者または許可済み運営担当者だけが個人情報管理・問い合わせ画面を閲覧。完了・法定保存保留には証跡参照とSHA-256が必須。期限超過・確認失敗はProduction monitorがCritical |
| 清掃                               | 既存カタログ同期ジョブを利用して日次で期限切れコード・セッションを各200件まで削除。解決済み90日超・保存保留なしの問い合わせだけ、管理者の明示操作で削除                 |
| 過去の平文                         | 管理画面または同期ジョブで各種200件ずつ暗号化。注文・返金・会計記録は自動削除しない                                                                                     |
| Shopify設定候補                    | `read_customers`・`write_customers`を除去し、注文Webhookの氏名・メール・住所入力を削減。設定ファイル変更だけでは実際の権限・購読は変わらない                            |

## 制約と残存データ

- 返品・撤回・本人確認・送金・契約など、法務上必要な連絡先、返送先、証跡は別モデルに残る。DB全体が個人情報ゼロになったとは扱わない。
- 以前にShopifyコレクションの公開metafieldへ同期された住所・説明は自動消去しない。公開済み内容を点検し、正規の公開プロフィールへ置き換える。
- 既存の平文店舗ログインセッションは互換読取りし、元の8時間の期限で失効する。必要なら管理画面で全店舗セッションを即時失効する。
- アプリ実行環境を侵害され、暗号鍵とDBの両方を取得された場合は復号され得る。暗号化はDB単独流出への対策であり、完全な侵入防止ではない。
- Shopify注文の氏名・住所への保護対象顧客データアクセスは配送・返品のため残る。顧客マスターscope削減だけで注文の個人情報アクセスが消えるわけではない。
- 既存バックアップやメール事業者の配信履歴はこのDB移行で消えない。バックアップの保存・失効と鍵の保全は別途管理する。
- 問い合わせの部分一致検索は最新1,000件の復号結果を対象とする。未解決・保存保留中の問い合わせは自動削除しない。
- `LEGAL_HOLD`は法定保存の判断根拠と本人への対応を記録した場合だけ使用する。データ削除の実施証明ではない。

## 本番反映順序

1. PRのQuality checksを通し、ストアが非公開、実決済・返金・進行中テストなしであることを確認する。
2. Renderに`PRIVACY_ENCRYPTION_KEY`を安全に設定する。値は暗号学的乱数32byteの64桁hex。平文をチャット・Git・ログへ出さない。既に設定された鍵を上書きしない。
3. 既存`PRIVACY_HASH_SECRET`を維持する。暗号化済みデータを扱う全プロセスで同じ暗号鍵を使う。鍵を作り直すと既存データは読めなくなる。
4. PR経由でmainへ反映し、Renderの既存preDeployで`20261008090000_minimize_personal_data`を適用する。破壊的カラム削除はない。起動・Shopify API・未適用migration・500を確認する。
5. 個人情報管理画面の旧データ件数を確認し、各バッチの暗号化と読取りを確認する。SQLや画面で平文を出力しない。サイトの公開・商品公開・決済操作はしない。
6. Shopify App Versionは未release候補を作成し、scope追加0、extension削除0、Function内容不変を確認してから反映する。現行versionをロールバック候補として保存する。
7. Renderの`SCOPES`と`SHOPIFY_APP_VERSION`を、実際にreleaseした設定へ揃える。既存SCOPES内の顧客masterの2scopeだけを除き、ほかの必要権限は落とさない。
8. Shopify Inboxの受信、お問い合わせページ、Shopify顧客アカウント・MFA・スタッフ権限は人間が確認する。問い合わせ経路の切り替えはこの確認後。

Shopify設定を変更するまでは旧scope・購読のままであること、鍵設定・デプロイ・過去データ暗号化が未実施なら本番の保存方式も未変更であることを報告する。

## ロールバック

暗号化開始後に旧mainへ単純ロールバックすると、旧コードは暗号文をメール・トークンとして使用して失敗する。
同じ鍵と新schemaを保ち、暗号文互換読取り・認証・ShopifySessionStorageを残す前方修正を優先する。
旧方式へ戻す必要がある場合は非公開状態で専用の変換計画・鍵保全・読取り試験を先に作る。
鍵を削除・再生成して復旧しようとしない。金融記録を初期化しない。migration rollbackや自動PII復号の一括書戻しは提供しない。
