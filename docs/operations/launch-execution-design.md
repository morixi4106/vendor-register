# 公開準備の実行設計

作成日: 2026-10-15 JST

状態: 第1段階をローカル実装・検証済み。本番反映、本番再監査、設定変更、公開、実決済は未実施。検証と再開地点は[進捗メモ](launch-progress.md)を参照。

## 結論

既存の公開判定、実地確認、国際販売ゲート、決済照合を維持し、不足の見える化と検証を3段階で進める。新しい管理アプリ、独自の税計算、別の公開許可エンジンは作らない。海外販売も初日から対応する目標は変えず、確認できない国を自動的に開けない。

進捗の正本は [公開準備の進捗](launch-progress.md)。この文書は実装方針と受入条件であり、P01-P28の完了証拠ではない。

## コード確認で分かったこと

| 現在あるもの | 設計上の扱い |
| --- | --- |
| `getProductionReadiness` と既存の `checks`、`canGoLive`、公開条件の適用区分 | 現在の設定に対する公開判定として維持。別の集計で上書きしない |
| `inspectOperationalReadiness` の実証跡と `ready`、期限・リリース不一致の理由 | 実際に確認済みかの根拠として利用 |
| 国内直販の期限付きリスク受容 | 未確認のまま例外扱いになることがある。確認済みと表示せず、海外へ適用できると推定しない |
| `ProductionReadinessPage` の国内直販向け案内 | 標準Checkoutの準備状態、販売全体の準備、海外販売の準備を分ける |
| 国別の証拠、商品別適合確認、配送受付、Shopifyへのゲート同期と読戻し | 作り直さず、対象国・商品・実際の配送経路と照合する |
| 本番取引probe、手動の証跡登録、受信確認 | 実装を再利用。自動収集結果で人間の確認や実取引を捏造しない |
| 公開前の監視メール抑止 | そのまま維持。調査や画面の追加に通知送信を付随させない |

特に、現在の画面には国内直販について「標準チェックアウトの準備ができています」「16シナリオと着金・返金は公開前の必須条件ではありません」という案内がある。国内の限定条件を海外販売全体の条件として読ませないことを最初の修正対象とする。これは静的なコード確認であり、稼働中の画面を今回再検証したものではない。

## 第1段階 確認結果と次の作業を整理

対象: P01-P09、P26、およびP16-P22への案内。

### 実装範囲

- 既存の本番前チェック画面を拡張する。新しいダッシュボード、公開API、Bearer token、DBテーブルは第1段階では追加しない。
- 現在の販売方式、観測日時、リリース、証跡不足、国内限定の例外、海外販売の未確認状態を区別して表示する。
- 実地確認の行から「不足の理由」「既存の確認画面」「必要な証拠」を特定し、優先順位の高い次の作業を最大3件提示する。
- `checks.status` がwarningであっても、実証跡の `row.ready` がfalseなら確認済みと扱わない。既存の `releaseDisposition` を保持して、条件付きの扱いと実確認を区別する。
- 未設定、取得失敗、期限切れ、リリース不一致、適用外を混同しない。適用外には既存ロジックによる理由を付ける。
- 海外対象が未設定で既存の国際検査がpassになっていても、海外販売の準備が完了したとは表示しない。
- 通知を停止した公開前状態を、業務メールの全面停止として扱わない。調査の再実行でメール、証跡登録、停止解除を行わない。

### 変更候補

- `app/components/readiness/productionReadinessPageState.js`
- `app/components/readiness/productionReadinessViewModel.js`
- `app/components/readiness/ProductionReadinessPage.jsx`
- 必要な安全なDTO項目に限り、既存の `app.production-readiness.jsx` のloaderを拡張。
- 対応するコンポーネント・route・契約テスト。既存の公開判定のexport契約とaction認可を維持する。

`getProductionReadiness` の返却値全体をログ・Git・外部レポートへ保存しない。検証記録には日時、チェックID、状態、理由コード、必要なリリース情報、件数のみを許可する。既存の認証済み経路を使い、新しい外部取得経路が必要なら別途設計する。

### この段階の完了条件

国内の購入制御が準備済みでも、P01-P09や海外販売まで完了したように表示されないこと。期限付き例外が「実確認済み」に化けないこと。次の作業が既存の適切な画面へつながり、再読込みや取得失敗で状態を改善させないこと。

## 第2段階 実際に販売する商品と国を検証

対象: P10-P11、P13-P14、P16-P22。

### 対象と不足の確定

1. 既存資料と読み取り権限の範囲で、運営直販の商品、実際の公開テーマ、販売候補国、決済、配送プロファイルを照合する。テーマのコピーと公開版を区別する。
2. 進捗メモに対象国・商品が確定した根拠を記録する。未確定ならそのまま未確定とし、海外機能OFFを理由に海外要件全体を完了扱いにしない。
3. 不足を「コード」「既存設定」「外部証拠」に分ける。既存の無効な機能は実装を調べてから扱い、同じ機能を再実装しない。

### 実装と検証

- コード不足だけをPRで修正し、国別証拠、商品別適合、税関情報、配送状況は既存モデルと保存経路へ統一する。対象国の法務・税務要件は、その作業時点の公式一次資料で確認する。
- アプリDB内の判定と、Shopifyの実設定・ゲート読戻し・実際のcheckout挙動を分けて検証する。
- 標準直販モードのValidation無効化を海外にも一律適用しない。国際ゲートを強制する実際の経路と販売方式を確認し、必要なら既存の検証付き経路への移行を別PR・承認対象として準備する。第三者販売を有効化する理由にはしない。
- 手動送料、無料配送、別Carrier Service、別配送プロファイルを含め、未承認の国や商品が購入できないことを検証する。
- PC・スマホで商品、カート、配送、合計、注文確認、失敗・重複操作を試験する。テストモードの成功と本番の実支払成功を区別する。
- 個人情報については過去の平文件数、公開情報、実権限、Webhooks、保存・削除経路を確認する。平文の出力、無承認の一括変換、鍵の再作成は行わない。

### この段階の完了条件

対象の商品・国・配送経路が明示され、その組合せでコード、証拠、Shopifyへの反映が整合すること。不許可国・証拠期限切れ・ゲート欠落・別配送経路での遮断を確認すること。設定やreleaseを伴う操作は、適用される承認境界を満たしてから行う。

## 第3段階 実取引と公開操作

対象: P04-P09、P12、P15、P26-P28。第三者店舗を公開する場合のみP23-P25も追加。

- 既存の権限設定・証跡で確認できる部分を先に済ませる。資金残高、MFA、銀行着金、実際の出荷、法務上の事実を推定で埋めない。
- 自動で確認できない項目は、必要な外部証拠と取得方法を一度に整理する。書類、アカウントへの適法なアクセス、実サービスの結果が必要な項目を、架空の確認者で登録しない。
- 承認範囲と決済上限を確認してから、既存probeで少額取引と照合を行う。返金、入金証明、国際注文の試験は採用する公開条件に従う。
- 取引の証拠を作成する前に、必要なコード・Shopify反映を完了させる。途中で対象リリースや決済方式が変わった場合は既存の紐付け・期限条件を再評価する。
- 緊急停止と復旧、隔離バックアップ復元は、それぞれの承認済み手順で実施する。本番DBへの復元や無断の販売停止・再開を自動テストへ混ぜない。
- 通知頻度、確認後の猶予、連絡先、独立監視の残課題を確定する。公開前はprelaunchのまま。本番通知への切替は公開とは独立した明示操作とし、送信試験は必要回数だけ行う。
- 最終判定の後、承認に従い公開する。公開後に入口、商品、checkout、初回注文、通知が期待どおりか追跡する。

## 検証方針

| 試験 | 期待結果 |
| --- | --- |
| 国内直販・海外対象なし | 現在の国内設定と海外未確認を分離して表示 |
| 国内限定のリスク受容あり・実証跡なし | 条件付きとして表示し、確認済みや海外承認にしない |
| 証跡欠落・失効・FAILED・リリース不一致 | 理由を保持し、対象項目を自動的に合格へ変更しない |
| 未使用のStripe・第三者機能 | 現在の方式で適用外なら設定を強制しない |
| データ欠落・API失敗・権限不足 | 不明または失敗として残す。空配列や件数0で成功を推定しない |
| 海外ゲートの欠落・失効・未承認国・北アイルランド・配送迂回 | 対象外の購入を許可しない。国内は別条件で検証 |
| 閲覧・再読込み・証拠収集 | 証跡upsert、設定変更、実決済、メール送信を実行しない |
| 画面のPC・スマホ表示 | 状態・理由・次の作業が読め、文字や操作部が重ならない |
| ログ・進捗記録 | 秘密、個人情報、受信コード、決済明細が出ない |

第1段階は純粋な表示整形の単体テスト、loader/actionの権限・副作用テスト、既存公開判定の契約テスト、画面スクリーンショットで確認する。以降は影響する決済・国際ゲート・個人情報の既存テストへ追加する。

## 今回変更しないもの

決済・返金のルール、既存証拠の有効期限、国内限定承認の範囲、販売許可フラグ、Shopify App Version、暗号鍵、バックアップ設定、監視メールの停止方針。第1段階でこれらの変更が必要になった場合は、表示改善に紛れ込ませず別の変更として設計する。
